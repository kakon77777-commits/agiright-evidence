When we say a model is “safer than its predecessor,” we mean that it scored better on a set of evals someone built. But a safety claim is only as sound as the eval behind it, and good ones are hard to build. A safety eval measures a model’s propensity to cause or contribute to harm, whether its response to a request makes harm more or less likely, and how severe that harm would be, rather than measuring specific capabilities. Safety first Build a team with the right skills Building a strong safety eval requires multiple perspectives, including from subject-matter and technical experts. Methods experts, for example, help decide how to sample, grade, and analyze the model’s responses.

Having domain and methods experts involved from the beginning of the process can mitigate against both. Run evals safely Safety evals often run with standard safeguards disabled so we can understand a model’s baseline performance. In cyber evals, in particular, models may probe the boundaries of their testing environments and could take unintended actions if they escape. For this reason, evals should be run in a sandbox with no internet access, and monitored in real time so you can stop a run immediately if a model is acting in ways that could result in real-world harm. In recent months, in response to our own incidents , we have hardened our evaluation environments , temporarily stopped running many evaluations that give models internet access, and implemented real-time monitoring for web search evaluations that require giving models internet access. We continue to work to make these environments both realistic and safe. Design Match the design to the question The first thing to ask when building an eval is: what is the question you’re trying to answer? This should guide the way you design the evaluation, as it will determine how you can interpret the results. If you deviate from the plan, say so in your report, and explain why. Sample size matters more than people expect. Model outputs are noisy and nondeterministic, so plan to run each test case several times and report the spread. We treat 100 items as the floor for a complex, multi-turn eval and 1,000 as the floor for a simpler, single-turn one. The larger your sample, the smaller the effect size you can detect. Small differences between models are easier to detect with paired comparisons , where you run both models on the same items and compute the confidence interval on the per-item differences rather than on each model’s aggregate score. Document everything Report the configuration you used, because it may affect performance. In our system cards, we report safety results for both our API—the raw model, as developers access it—and for claude.ai, where the system prompt is applied. In testing Claude Fable 5.1, the difference in the appropriate response rate between these two configurations on our multi-turn safety evals was as high as 34 percentage points. Provide enough detail (such as model versions, sampling settings, prompts, grader version, and dates) that someone else could reproduce the run, and don’t compare scores from different graders, because they may grade the models slightly differently. Disclose flaws responsibly When we were reviewing transcripts from our suicide and self-harm evaluations prior to the release of Claude Fable 5.1, we observed that Claude sometimes implicitly validated self-harm as a coping strategy, even within responses that discouraged self-harm and pointed the user toward human support. We therefore added an instruction to the system prompt (“Claude does not tell someone that self-harm works, helps, or does something for them, even when they say so themselves”) to minimize this behavior. Re-running the eval with this and other targeted system prompt mitigations showed that the changes to our system prompt significantly improved the appropriate response rate on claude.ai (60% on the API vs 94% on claude.ai with the new system prompt). For this reason, it’s also helpful to run evals continuously during the model development process rather than once before release. Many of our safety evals run against model snapshots throughout fine-tuning. The results then go to our Safeguards and Model Behavior teams, and we can often quickly make adjustments to reward signals or system prompts before release. When an eval turns up a severe flaw in a deployed system, disclose it responsibly: tell the developer (whether that’s an internal team or an external organization) and give them time to fix it before you publish your results, so the flaw can’t be exploited in the meantime. This is the central principle of responsible disclosure . Where to start Not every eval necessarily needs to employ every recommendation in this post, but we believe a good eval should follow as many as possible. If you only do three things, do these: write down the construct you want to measure before collecting data, validate your grader against human judgment before trusting any number it produces, and report uncertainty so readers can tell signal from noise. As evaluation science continues to mature, these recommendations may evolve. For now, we hope they can help the community build the safety evals we need to ensure our models remain safe, helpful, and harmless.
