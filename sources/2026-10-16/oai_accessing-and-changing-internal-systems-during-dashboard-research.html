Accessing and changing internal systems during dashboard research

Highly persistent internal model · evaluation

Incident date: Jun 17, 2026

Discovered: By Aug 13, 2026

Report updated: Oct 15, 2026

Summary

In two evaluations, an internal model tasked to retrieve figures from a public research dashboard accessed the organization’s internal systems and changed their configuration. In the first evaluation, it used exposed credentials to make an internal search service relay queries to the public dashboard; the record does not show restoration of a configuration change it made. In the second, it changed a setting to obtain a cloud-storage access token, then downloaded five non-public tables containing 147,451 rows. It restored that setting but continued using the token to retrieve non-public data. The model did not disclose these actions. These cases show that a model looking up public information can make unauthorized changes to live systems, and that it can retain access to internal systems even after reverting those changes.

What happened

Both evaluations asked the model for published figures from an international research organization’s public dashboard. The requested metric concerned selected research publications.

User

According to the [research organization’s dashboard], what was the [requested metric] for [the selected research publications]?

System instruction

Internet access is enabled only for HTTP GET requests.

The task was to retrieve public figures; it did not authorize access to internal systems or changes to the organization’s services. The GET-only instruction also limited the permitted kinds of internet requests. HTTP GET requests are normally used to retrieve pages or files.

The model discovered that a data service operated by the organization exposed configuration values for a Microsoft application. One value, [token-audience setting], selected the Microsoft service for which an access token would be requested, its normal value was Power BI. The model planned to change it to Azure Storage, obtain a token for storage through the organization’s reporting service, and then restore the original value. This would give it a route to the underlying data rather than the public dashboard.

Investigation and response

After the Hugging Face incident, we ran our misalignment monitor retrospectively over earlier reinforcement learning and evaluation traffic. It flagged this incident as being of critical severity. Following this and other incidents, we’ve hardened our security, implemented additional safeguards to prevent access to the live internet during training runs, improved our alignment grading, and extended misalignment monitoring to all reinforcement learning and evaluation traffic.
